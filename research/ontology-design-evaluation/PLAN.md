# 금융 공시 온톨로지의 설계·표현 방식·AI 평가 조사 계획

작성일 2026-11-13. 사용자 요청에 따른 조사 계획이다. 최종 기술 선택과 온톨로지 변경은 후속 조사 결과를 보고 결정한다.

## 목표와 기본 전제

목표는 다음 질문에 근거와 재현 가능한 예제로 답하는 것이다.

1. 목적과 데이터가 주어졌을 때 좋은 온톨로지를 판정하는 기준은 무엇인가?
2. RDF, RDFS, OWL, SHACL, LPG는 어떤 차원에서 비교하고 함께 사용할 수 있는가?
3. 금융 공시에서 필요한 식별·시간·상태·근거·정정 이력을 각 방식으로 어떻게 표현하는가?
4. AI가 만든 정의서의 의미, 구조, 제약, 요구사항 충족도를 어떻게 독립적으로 검증하는가?
5. 실제 공개 사례와 연구는 무엇을 입증하며 우리 프로젝트에 얼마나 적용 가능한가?
6. 현재 v0.1의 장점과 미해결 항목을 어떻게 측정하고 개선하는가?

계획의 작업 가정은 근거를 추적할 수 있는 공시 질의·분석을 1차 목표로, 시장 데이터·팩터·예측 연계를 2차 목표로 둔다. 시점 재현은 두 목표 모두에서 평가한다. 주가 예측 성과는 시세 품질과 예측 모델 등에도 영향을 받으므로 온톨로지 자체의 평가와 구분한다.

현재 환경은 Neo4j Community와 Python 파이프라인이다. 승인된 CPU 4 vCPU/16GiB·320시간과 시간 단위 갱신 구상은 운영 검토의 입력 조건으로 사용한다. 시간 단위 갱신과 총 가동시간 예산의 양립 여부도 확인한다.

## Phase 0 — 기존 정의서와 공식 문서 발견

계획 단계에서 확인한 자료는 `ontology/v0.1/`의 README와 CSV 5개, `queries/examples.cypher`, `queries/verify.cypher`, `queries/market_examples.cypher`다. 전체 공시 원문은 읽지 않았다.

현재 확인한 사항은 다음과 같다.

- 25개 개념과 33개 관계가 제안돼 있다. README는 팀 검토용 논리 정의 초안이라고 명시한다.
- 공개 시점, 효력 기간, 시스템 기록 기간을 구분하고 정정 이력을 보존하도록 설계돼 있다.
- Assertion, EvidenceSpan, DocumentVersion, ExtractionRun으로 주장과 근거·추출 이력을 연결한다.
- V01–V18은 자연어 검증 규칙이다. 모든 규칙의 실행 가능한 구현 여부는 아직 확인하지 않았다.
- 예시 쿼리와 속성 사전의 일부 필드명을 대조해야 한다. 예를 들어 `scope`와 `aggregation_scope`, `line/path`와 근거 위치 필드의 관계를 확인한다.
- URI 정책, 전체 다중성, 이벤트 역할 목록, 수치 정밀도와 열거형 확장 절차는 후속 결정 항목이다.

공식 개념 문서는 RDF 데이터 모델, OWL의 의미·추론, SHACL의 RDF 검증, Neo4j 속성 그래프를 구분하는 데 사용한다. 후속 조사에서 최신 표준 상태와 실제 사용 버전도 다시 확인한다.

- [W3C RDF Concepts](https://www.w3.org/TR/rdf11-concepts/)
- [W3C OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)
- [W3C SHACL](https://www.w3.org/TR/shacl/)
- [Neo4j graph database concepts](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)

이 단계는 API 구현을 다루지 않는다. 후속 PoC에서는 선택한 버전의 공식 문서와 실행 가능한 예제를 근거로 사용 API를 확정한다.

검증 결과물은 현재 상태 목록과 미확인 사항 목록이다. 자연어 설계 규칙을 이미 구현된 DB 제약이나 OWL 공리로 간주하지 않는다.

## Phase 1 — 사용 목적과 평가 질문 고정

핵심 Competency Questions(CQ) 10–15개를 먼저 정의하고 경계·부정 사례를 더해 약 20–30개의 평가 질문을 구성한다. 각 질문에 필요한 데이터, 개념·관계, 시간 의미, 기대 결과, 근거 위치를 연결한다.

우선 후보는 다음과 같다.

| 질문 또는 사례 | 확인할 설계 능력 |
|---|---|
| 특정 회사에 관한 공시의 제출인은 누구인가? | 공시 대상회사와 제출인 구분 |
| 같은 회사의 보통주·우선주 보유 현황은? | 회사·증권·상장, 수량·비율·분모 구분 |
| 특별관계자 합산과 개인 보유를 구별할 수 있는가? | 집계 범위와 역할 표현 |
| 정정공시 이전 시점에 알려진 계약금액은? | 원문 버전, 당시 가용 정보, 정정 전후 주장 |
| 이사 후보자·선임 결의·재임은 어떻게 다른가? | 역할과 이벤트·상태 구분 |
| 인수 결정 공시를 완료 사실로 해석하는가? | 예정·결정·완료·철회 상태 |
| 상대방 비공개 계약을 어떻게 표현하는가? | 미공개·미확인과 엔티티 식별 |
| 같은 기업의 연결·별도, 누적·분기 재무는? | 관측값의 기간·범위·단위 |
| 같은 업종인 두 기업을 경쟁사로 볼 수 있는가? | 원문 주장과 추가 추론의 구별 |
| 한 관계의 원문 표·문단과 추출 실행을 찾을 수 있는가? | 근거와 계보 추적 |

현재 정의서 V01–V18과 예시 쿼리를 출발점으로 사용한다. 아직 표현 가능한 사실의 종류와 실제 추출·적재가 완료된 범위를 분리해 기록한다.

검증은 질문별 정답·허용 가능한 대안·응답 유보 조건을 사람이 검수하는 방식으로 한다. 온톨로지 생성에 사용한 질문과 최종 검증용 질문·문서를 구분한다.

## Phase 2 — 논문·사례·기술 문서 근거 수집

핵심 논문 약 12–18편을 검토 대상으로 정하고, 그중 주요 방법론과 직접 관련 실험은 본문까지 읽는다. 실제 사례 약 4–6건과 공식 기술 문서를 연결한다. 범위는 고전 설계 원리부터 2026-11-13까지 확인할 수 있는 AI 기반 구축·평가 연구다.

| 갈래 | 조사할 내용 | 출발 자료 |
|---|---|---|
| 설계 원리·요구사항 | 명확성, 정합성, 역할·동일성, CQ, 최소 가정과 확장성 | Gruber, Grüninger & Fox, OntoClean |
| 품질 평가 | 구조 지표, 목적 적합성, 모델링 오류, 검증 범위 | OntoQA, OQuaRE, OOPS! |
| AI 생성·평가 | CQ와 원문 기반 생성, 불필요한 요소, 관계·공리 오류, 전문가 평가 | Ontogenia 계열, Domain-OntoGen, CQ4OE, 최근 체계적 문헌조사 |
| 금융·실무 사례 | 공통 식별자, 표준 재사용, 재무 의미, 근거·시간, 운영·갱신 | FIBO, GLEIF 등에서 공개 자료와 구현을 우선 탐색 |
| 표현·구현 | RDF/RDFS, OWL 프로파일, SHACL, LPG, 표준 매핑과 운영 비용 | W3C, Neo4j 등 공식 문서와 공개 구현 |

이미 대화에서 확인한 논문은 출발 목록으로 재사용한다.

- [Gruber의 설계 원리](https://tomgruber.org/writing/onto-design.pdf)
- [OntoClean](https://www.loa.istc.cnr.it/old/Papers/CACM2002.pdf)
- [OQuaRE](https://research.manchester.ac.uk/en/publications/oquare-a-square-based-approach-for-evaluating-the-quality-of-onto/)
- [Ontology Generation using Large Language Models](https://arxiv.org/abs/2503.05388)
- [CQ4OE](https://arxiv.org/abs/2609.26029)
- [LLM 기반 온톨로지 엔지니어링 체계적 문헌조사](https://journals.sagepub.com/doi/10.1177/22104968261465514)

각 자료는 주장, 실제 평가 대상, 데이터·질문, 비교 기준, 측정 지표, 재현 자료, 한계, 우리 프로젝트 적용성을 기록한다. 저널·학회·워크숍·프리프린트·공식 문서·벤더 사례를 구분한다. 기술 블로그는 작성자의 직접 경험과 공개 코드·설계도를 확인하고 성능 주장은 별도로 검증한다.

FIBO 같은 표준의 존재, 벤더의 도입 소개, 실제 운영 효과를 각각 다른 증거 수준으로 취급한다. 기존 대화와 README의 TRACE 등 연구도 원문 식별과 실험 조건을 확인한다. 공개 자료로 확인할 수 없는 구현·성과는 미확인으로 표시한다.

검증 결과물은 출처별 근거표와 사례 비교표다. 표현 방식 간 우열을 평가할 때 서로 다른 데이터·작업의 벤치마크 수치를 직접 비교하지 않는다.

## Phase 3 — 표현 방식 선택 기준과 후보 설계

개념 모델, 의미·공리, 저장 모델, 검증 규칙, 질의·추론 엔진을 구분해 비교한다. RDF와 OWL, LPG가 실제로 어떤 조합을 구성하는지부터 설명한다.

우선 비교 후보는 다음과 같다.

1. Neo4j LPG와 명시적 스키마·Cypher 검증 규칙.
2. RDF/RDFS와 SHACL, SPARQL.
3. RDF와 목적에 맞는 OWL 프로파일·추론기, SHACL.
4. 의미 정의를 RDF/OWL로 관리하고 LPG를 서비스 조회에 사용하는 혼합 구조. 이 후보는 동기화·매핑 유지 비용까지 평가한다.

각 후보를 외부 데이터 결합, 식별자·표준 재사용, 요구 추론, 데이터 검증, 시간·근거 표현, 다중 참여자 이벤트, 조회 복잡도, 갱신, 디버깅, 학습 비용, 실행 환경·라이선스 기준으로 평가한다. Neo4j Community에서 제공하는 기능과 추가 기능을 구분한다.

설명에는 공개 세계 가정, 미상과 거짓, 동일성, 다중성, OWL의 추론과 입력 데이터 검증의 차이, 엣지 속성과 n-ary 관계를 포함한다. 모든 도구에 동일한 수준의 형식 의미가 제공된다고 가정하지 않는다.

검증 결과물은 필수 조건과 선호 조건을 구분한 의사결정표다. 실제 요구된 추론 사례 없이 OWL 도입 효과를 추정하지 않으며, 운영 편의만으로 의미 정의의 적절성을 판정하지 않는다.

## Phase 4 — 우리 프로젝트의 품질 평가 체계

평가를 세 층으로 나눈다.

| 평가 층 | 측정할 내용 |
|---|---|
| 온톨로지·논리 정의 | CQ 표현 가능성, 개념·관계의 적절성, 논리적 정합성, 제약, 중복, 변경 영향 |
| 추출·매핑·적재 데이터 | 원문 대비 관계·속성 정확도, 누락, 식별·단위·시간 오류, 근거 추적률 |
| 조회·응용 결과 | 기대 답과의 일치, 근거의 타당성, 시점 재현, 잘못된 사실의 반환, 응답 시간 |

실제 공시 약 40–60건을 공시 유형과 경계 사례에 따라 선정하는 것을 초기 범위로 잡는다. 표본 개수는 드문 정정·철회 사례의 확보 상황에 따라 조정한다. 자동 제약을 시험할 인위적 오류 사례 약 10–20건은 실제 공시와 구분해 사용한다.

오류가 없다는 검사 결과와 필요한 구별을 표현할 수 있다는 결과를 함께 확인한다. 예를 들어 제약이 전혀 없어 검사 오류가 없는 모델, 빈 조회 결과만 반환하는 모델을 좋은 설계로 판정하지 않도록 한다.

필수 통과 조건과 상대 비교 지표를 분리한다. 핵심 CQ, 주요 의미 오류, 미래 정보 누출, 근거 연결 등은 우선 통과 조건 후보로 검토한다. 범용 합격 점수나 임의의 가중 합산 점수를 논문 표준처럼 제시하지 않는다.

검증 결과물은 지표 정의, 계산식·분모, 평가 데이터, 기대 결과, 실패 예시를 담은 평가표다.

## Phase 5 — AI 온톨로지 생성·검증 절차

동일한 요구사항·원문·예산에서 자유로운 초안 생성과 CQ·정의·근거·제약을 제공한 생성 방식을 비교하는 실험안을 만든다. 전체 공시를 한 번에 모델에 넣지 않고 선정한 표본과 필요한 문단·표를 사용한다.

모델·프롬프트·입력 문서·버전·토큰 비용을 기록하고 대표 조건은 반복 생성해 변동성을 확인한다. AI 생성 문서의 자기평가와 정답 평가를 구분한다. LLM 판정은 전문가 검토와 실행 가능한 검증 결과를 보조하는 용도로 평가한다.

검증 결과물은 생성용 입력 템플릿, 검토 항목, 오류 분류와 재현 절차다. AI가 생성한 CQ와 그 AI가 생성한 온톨로지만으로 완결된 평가를 만들지 않는다.

## Phase 6 — 동일 사례의 소규모 비교 실험

조사에서 선정한 핵심 사례 3–5개를 같은 정답과 의미로 각 표현 방식에 모델링한다. 가능한 PoC 범위는 작은 표본 스키마, 샘플 인스턴스, 조회·검증 예제다.

우선 사례는 정정 전후 계약금액, 보유 현황과 증권 종류, 임원 역할·기간, 비공개 상대방, 근거와 추출 주장이다. 현재 `ACTION_PARTICIPANT`의 엣지 role과 ContractParticipation의 노드 역할 표현도 비교 입력으로 삼는다.

질문에 대한 응답, 의미 보존, 검증 오류, 필요한 추론, 코드·모델 복잡도, 변경 작업량을 비교한다. 성능을 측정하면 하드웨어·버전·인덱스·캐시·측정 범위를 명시한다. 작은 PoC의 속도를 대규모 금융 운영 성능으로 일반화하지 않는다.

## Phase 7 — 종합 판단과 팀 공유 자료

최종 산출물은 다음과 같다.

1. 의사결정 요약과 현재 프로젝트에 대한 권고·근거·전환 조건.
2. RDF·OWL·SHACL·LPG의 관계와 선택 기준 비교표.
3. 논문·실무 사례 근거표와 읽기 순서.
4. 프로젝트 품질 평가표, CQ·정답·반례 세트.
5. 현재 정의서의 항목별 검토 결과와 개선 우선순위.
6. 비교 PoC를 수행한 경우 해당 모델·질의·검증 예제와 실행 결과.
7. 팀 공유용 정의서 템플릿. 개념·관계·식별·시간·상태·단위·근거·제약·표준 매핑·예시·반례·변경 이력을 연결한다.

보고서에서는 문헌에서 확인한 사실, 로컬 데이터에서 관찰한 결과, 설계자의 판단과 미확인 사항을 구분한다. 특정 기술을 추천하면 그 추천이 달라지는 조건도 함께 적는다.

## 진행 순서와 비용 관리

- 첫 점검 지점은 Phase 0–2의 요구사항·문헌·사례 근거표다.
- 다음 점검 지점은 Phase 3–5의 선택 기준과 평가·AI 생성 절차다.
- 마지막 점검 지점은 Phase 6–7의 작은 비교 실험과 프로젝트 권고다.

자료 검색·요약은 중복을 줄여 축적하고, 원문 확인과 출처별 한계를 기록한다. 공시 선정은 목록·제목·문서 구조로 먼저 좁힌 뒤 관련 표·문단을 읽는다. 검증용 정답과 경계 사례를 확정하면 반복 검사는 가능한 한 로컬 코드로 실행한다. 의미 모델을 비교하는 데 필요한 범위 안에서 도구 실험과 추가 데이터 읽기를 제한한다.
